# Decision log

Every non-obvious rule the solution adopts, with the data evidence that justified
it. Measured counts referenced here come from
[`data_facts.md`](./data_facts.md), regenerated by
`python code/scripts/profile_dataset.py`.

---

## D1 — Package layout avoids every stdlib name collision

**Decision.** One package, `code/audit/`, with sub-modules. No top-level package
under `code/` may be named after a standard-library module.

**Why.** `python code/main.py` puts `code/` on `sys.path`. A package named
`code/io/` would then satisfy `import io` for the whole process, breaking
`open()`, `csv`, `json` and anything else that reaches for the stdlib `io`. The
same hazard applies to `types`, `logging`, `json`, `csv` and `code` itself. The
earlier proposed layout had exactly this defect.

**Consequences.**

- `code/tests/` deliberately has **no** `__init__.py`. Making it a package would
  name it `code.tests` and shadow the stdlib `code` module. Imports work through
  `code/tests/conftest.py`, which inserts `code/` into `sys.path` the same way
  `main.py` does.
- `code/evaluation/main.py` stays the evaluation entry point, as shipped in the
  starter repo.

## D2 — Output rows are sorted by the integer suffix of `case_id`

**Decision.** `output.csv` is written in natural numeric order of the case
number. Implemented as `loaders.case_sort_key`, a sort key on the integer
suffix, never by trusting the input file's order.

**Why.** `deletion_requests.csv` runs `case_33` through `case_550` without zero
padding, so lexicographic sorting puts `case_100` before `case_99`. The dataset's
own order is numeric. Sorting explicitly rather than preserving input order means
the guarantee holds even if the input is reordered or filtered with `--cases`.

**Evidence.** The 518 requests are already in ascending numeric order
(`test_requests_are_in_natural_numeric_order`), so the key reproduces the file's
order exactly while being robust to a reordered input.

**Test.** `test_case_sort_key_is_numeric_not_lexicographic` asserts `case_9 <
case_10 < case_99 < case_100` and asserts that plain `sorted()` disagrees.

## D3 — Step order is the problem statement's table order, with no dependency pass

**Decision.** Within a phase, steps sort by the operation's position in the
problem-statement table, then `system_id`, then `resource_id`. There is no
separate dependency-reordering stage.

**Why.** The table already orders remediation so that process-level actions
precede record-level ones: `DISABLE_DATA_FLOW`, `BLOCK_RESTORE`,
`DELETE_RECORD`, `REDACT_RECORD`, `ANONYMIZE_RECORD`. The safety requirement in
AGENTS.md §6.5 — stop flows and block restores before changing dependent records
— is therefore satisfied by the table order itself. An additional dependency pass
could only reorder steps *away* from the specified order.

**Evidence.** Zero of the 32 sample cases have out-of-order phases, and zero have
non-consecutive `step_no` (`data_facts.md` §6.7). Sample case_11 shows the
remediation sequence `DISABLE_DATA_FLOW`, `DELETE_RECORD`, `REDACT_RECORD`,
`ANONYMIZE_RECORD`, matching the table.

**Implementation.** `models.OPERATION_RANK` is derived from the declaration order
of the `Operation` enum, which is written in table order, so the two cannot drift
apart. `test_operation_rank_follows_the_problem_statement_table` pins it.

## D4 — `state` is derived from `operation`, never chosen

**Decision.** `models.OPERATION_STATE` maps each of the 15 operations to its one
permitted state. Step construction takes an operation and looks the state up.

**Why.** The contract pairs them one-to-one. Treating `state` as an independent
field invents a way to emit an invalid pair and costs field-level accuracy for
nothing.

---

## D5 — Timestamps are timezone-aware UTC from load time

**Decision.** `loaders.parse_timestamp` converts every dataset timestamp to an
aware UTC `datetime` at the boundary.

**Why.** Every decision in this problem is a comparison against a case's
`audit_at`. Mixing naive and aware datetimes raises `TypeError` at best and
compares wrongly at worst. Normalising once at the edge means no downstream
module has to think about it.

**Evidence.** All dataset timestamps carry a trailing `Z`; capture times and
`audit_at` values overlap in the same window (2026-01-29 to 2026-10-01), so
admissibility is decided per case and the comparisons are frequent.

---

## D6 — `sample_output.csv` is read only by the evaluation harness

**Decision.** The audit pipeline never opens `sample_output.csv`. Only
`code/evaluation/` does.

**Why.** AGENTS.md §6.7 forbids hardcoded golden labels and case-family
shortcuts. Keeping the file out of the pipeline's reach makes that structural
rather than a matter of discipline. `config.yaml` lists the sample paths under
`paths` for the harness; the pipeline reads `requests_file` only.

## D7 — Request intent is classified by the model, not by keywords

**Decision.** Whether `request_text` authorises deletion is an LLM decision.
Keyword cue lists exist only inside `code/scripts/profile_dataset.py`, which is
read-only recon and is not imported by the pipeline.

**Why — measured.** The dataset contains **negation traps**: non-deletion
requests that state a deletion keyword precisely in order to refuse it.

> "Please stop the promotional emails. I still need the account and my order
> history, so I am not asking for deletion."
>
> "Can you tell me what personal information you hold about me? This is an
> information request, not a request to erase it."
>
> "Could you send me a copy of the information held on my account? I still use
> it, so please don't delete or change anything."

Three of the ten non-deletion candidates are of this form (`data_facts.md` §4.4).
A cue list decides all three backwards. Requests also arrive in English, French,
Spanish, Portuguese, Japanese and Korean (§4.3), so the cue list would have to be
maintained per language as well.

**Cost control.** 375 of the 518 request texts are distinct once emails and
digits are masked (§4.5), so a cache keyed on the normalised text bounds
classification at 375 calls rather than 518 — about a 28% reduction before any
other batching.

**Not yet decided.** There are 10 `CLASSIFY_REQUEST` activity rows from
`privacy_intake` that state a request was classified as non-deletion. They agree
with the candidate set in size. Whether to use them as a signal, a cross-check,
or not at all is open: a non-deletion case that intake never classified would be
missed by relying on them. Tracked as open item 10 in `data_facts.md` §7.

## D8 — `system_id` comes from the resource's owning system, not the activity target

**Decision.** The `system_id` of a step is derived from the `resource_id`
prefix, using the owning-system mapping, not from the `target_system` of whatever
activity row mentions the resource.

**Why — measured.** In the sample answers the prefix-to-system mapping is strictly
one-to-one (`data_facts.md` §6.6): `account`→`account_service`,
`search`→`search_service`, `support`→`support_platform`,
`analytics`→`analytics_platform`, `audit_record`→`security_service`,
`data_flow`→`integration_service`, `backup`→`backup_service`,
`export`→`export_service`, `tombstone`→`identity_service`.

The activity stream does **not** respect that mapping: 232 rows route `support_*`
resources through `target_system=search_service`, and 155 route `export_*` through
`object_store` (§2.4). Deriving `system_id` from activity rows would therefore
emit `search_service` for a support record and fail field-level accuracy.

## D9 — Evidence citations prefer a `file_id`, and are stored per observation

**Decision.** Findings and `COMPLETE` verification steps cite an
`evidence_files.csv` `file_id`. `activity_id` and `audit_id` remain permitted
fallbacks but are not the default. **The citation is carried by each individual
observation, not by the case.**

**Why — measured.** All 75 evidence citations in `sample_output.csv` resolve
against `evidence_files.csv`; none is an `activity_id` or an `audit_id`
(`data_facts.md` §6.5).

**Amended.** The first version of this decision also concluded that a case is
anchored on one file, because 31 of 32 sample cases cite a single distinct
evidence id. That reading was wrong as a data-model constraint. The generated
cases cite one case-level snapshot, but the hand-built cases (the `account_00N`
family, with screenshots, PDFs and data-catalog links) cite the specific file
that proves each resource's state: sample `case_04` cites `evidence_54` for the
account and `evidence_56` for the analytics record.

So `evidence_id` lives on `Observation`, one per fact, and "one file for the
whole case" is a *selection heuristic* applied when choosing which of several
competing proofs to cite — not an assumption baked into ingestion. Had it been
baked in, every hand-built multi-file case would have been unfixable later.

## D10 — Replication drift is a remaining record

**Decision.** A resource present in a replica copy and absent from the primary
is a remaining record: `REPORT_REMAINING_RECORD` → `DELETE_RECORD` →
`VERIFY_RECORD_ABSENT`.

**Why — measured.** Sample `case_05`: `evidence_54`
(`customer_accounts_failover_replica_20260902.sql`) holds two tables.
`customer_profiles_primary` does not contain `account_005`;
`customer_profiles_failover_replica` holds it with `account_status = ACTIVE`. The
gold answer is exactly those three steps. A deletion that succeeded on the
primary is therefore not complete while a replica still serves the row.

**Implementation.** `Observation.copy_label` carries where a copy lives, taken
from the SQL table suffix (`primary`, `read_replica`, `reporting_replica`,
`failover_replica`, `replica_<region>`). `EvidenceIndex.copies_of` returns the
latest observation per copy label, so drift is a disagreement between two entries
of one dictionary rather than something a caller has to go looking for.

## D11 — Keep the most specific time on every observation

**Decision.** `observed_at` is the record's own time where it has one, then the
enclosing snapshot or scope time, then the file's manifest `captured_at`. Never
the other way round.

**Why — measured.** Times inside a file routinely disagree with the file's
capture time, and the inner time is the fact:

- log lines predate their file's `captured_at` by days
  (`application_trace_eu_north_20260302.log` carries 2026-02-22 lines);
- JSON records carry their own `observed_at` or `recorded_at`;
- snapshot bundles carry a per-snapshot `captured_at` under one `exported_at`;
- SQL inventories carry `snapshot_scope(origin_system, captured_at)`, so two
  systems in one file can have different scope times;
- `operational_record_history` collections hold several timed readings of the
  *same* resource, which must all survive — a case's `audit_at` then selects
  among them.

Using the file time would date a February reading to March and change which
side of a cutoff it falls on.

**Implementation.** `fields.most_specific_time`, with the fallback chain passed
explicitly by each parser.

## D12 — Absence is proved by coverage, not by a missing id

**Decision.** When a snapshot enumerates a system copy at a time, that is
recorded as a `CoverageFact`. A resource is provably absent from that copy when
coverage exists and no observation from the same artefact and copy mentions it.

**Why.** A resource id that does not appear in a file proves nothing by itself —
the file might simply not be about that resource. It proves absence only if the
file claimed to list everything. Three forms of that claim appear in the data:
`snapshot_scope` rows in SQL inventories, `data_store` + `captured_at` +
`records: []` in JSON bundles, and a typed SQL table whose base name identifies
its system.

**Measured confirmation.** 4 of the 75 sample citations are of exactly this
shape: `case_01`, `case_02` and `case_04` cite `evidence_54` to prove
`account_001`/`002`/`004` absent, and `case_31` cites `evidence_51`
(a bundle whose `customer_profiles` list is empty) for `account_4857`. All four
gold operations are `VERIFY_RECORD_ABSENT`. `evidence_90`
(`customer_data_inventory_20260905.sql`) is the purest example: one `INSERT`,
into `snapshot_scope`. It is an artefact whose entire content is a claim of
absence. 369 coverage facts come out of ingestion in total.

## D13 — A log trace is merged into one observation per resource

**Decision.** Log lines sharing a `trace_id` / `requestId` are merged, one
observation per distinct resource in the trace. Lines with a resource but no
trace stand alone. Lines with neither are dropped.

**Why — measured.** Several log styles split one fact across two lines: the
`*_started` line carries the lookup key (`lookup_key`, `match_key`,
`subject_key`, `correlation_key`, `scan_key`) and the `*_completed` line carries
`resource_id` plus the result. Parsed independently, the state would have no
identity and the identity would have no state, and the resource could never be
attributed to a person. Other styles (`record_lookup` with `seq=N`) put
everything on one line, which is why both paths are needed.

One trace can touch two systems, so the merge is keyed on (trace, resource)
rather than on trace alone, and each resource keeps its own `system_id` while
inheriting the trace's identity links.

## D15 — A completed read, scan or heartbeat proves the record exists

**Decision.** When a log line gives no explicit presence signal, an event whose
name *ends* with `_completed`, `_read`, `_loaded`, `_scan`, `_evaluated` or
`heartbeat` is taken as proof that the named resource exists. Explicit signals
(`http_status`, `rows`, `result`) always win; failure events
(`*_failed`, `*_error`, `*_abandoned`, `*_denied`) prove nothing.

**Why — measured.** Before this rule, 228 of 2,893 observations had
`present = None`, and they were the wrong 228. They included every
`message_pii_scan` line (30), every `analytics_identity_scan` (14), every
`attachment_pii_scan` (7) and every `connector_heartbeat` (24). Those lines are
the entire evidential basis of two finding types:

- `message_pii_scan resource_id="support_9464" matched_value="silva.mariana@icloud.com" detector="direct_identifier"`
  → the support message still exists **and** still exposes a direct identifier,
  which is a `REPORT_EXPOSED_PII` finding;
- `connector_heartbeat resource_id=data_flow_1121 enabled=true scheduler_registered=true`
  → a `REPORT_ACTIVE_DATA_FLOW` finding.

Discarding them as "state unknown" would have made those findings unreachable
from the logs.

**Why it is safe.** The full event vocabulary of the 26 log files was
enumerated: 31 distinct events name a resource, and every `*_completed`,
`*_read`, `*_loaded`, `*_scan` and `*_evaluated` one reports a read. None reports
a deletion — deletions are claims in `system_activity.csv`, which is not an
evidence source (D14). Matching on the event's *ending* rather than a substring
matters: `analytics_profile_read_started` contains `_read` but is not a
read-back, and a lone started line must stay unknown.

**Result.** `present = None` fell from 228 to **1**: a single
`thumbnail_failed` line, where a preview renderer failed on an unsupported
media type. That genuinely establishes nothing about the attachment.

## D14 — `system_activity.csv` is not an evidence source

**Decision.** The activity stream produces no `Observation`. It is loaded, but
handled separately as a stream of *claims*.

**Why.** AGENTS.md §6.6 says activity results are claims unless evidence
establishes the resulting state, and the numbers bear it out: `DELETE_RECORD`
activity is 302 `SUCCESS` against 368 `FAILED` and 220 `PARTIAL`
(`data_facts.md` §2.2). Mixing claims into the same store as observed state would
make it impossible to keep the distinction the problem is built on. The
`activity_id` remains available as a citation of last resort.

## D16 — Identity matching is exact, never fuzzy

**Decision.** The request email is matched case-insensitively against
`user_identities.email`, then against historical email values in
`user_audit_log`. Nothing else. No fuzzy matching of names or look-alike
addresses, and a name is never an identifier.

**Why — measured.** The dataset plants look-alikes deliberately, and one sample
case says so outright. Sample `case_28` is filed by `smartinez6461@gmail.com`
and its request text reads:

> "A search result with a similar email belongs to someone else, so please do
> not treat that record as mine."

`user_identities.csv` indeed holds `mmartinez7917@gmail.com` (user_652) and
`a.martinez76@gmail.com` (user_613). Worse, `customer_search_primary_20260910.sql`
holds three near-identical rows in one table: `jonas.berg@outlook.com`
(`search_001`), `jonas.berglund@outlook.com` (`search_8814`) and
`joana.berg@outlook.com` (`search_4203`). Sample `case_06`'s gold cites
`search_001` only. Any edit-distance matching would attribute all three.

**Supporting fact.** `data_facts.md` §3.4 measured **zero** identifier
collisions across users, so exact matching loses nothing: there is no case where
a user's own identifier is ambiguous.

**Resolution order.** The current snapshot wins over the audit log: if an address
is somebody's live email, that is who filed the request. An address held
historically by two different users resolves to nobody rather than to a guess.

## D17 — Attribution is scoped to a deletion episode

**Decision.** A resource is in scope for a case only if at least one linking
observation falls within `[requested_at − 7 days, audit_at + 7 days]`.

**Why.** The same person can file more than one deletion request months apart,
and users with two cases exist in the data. Without a time scope, a link
observed during the February episode would be attributed to the August one, and
the August case would report records that were legitimately handled months
earlier.

**Why the slack is asymmetric in effect.** The upper slack is load-bearing:
sample `case_23`'s security audit record is only linked in a bundle captured two
days *after* `audit_at`, and the gold answer still verifies it. Linkage evidence
may come from a file captured after `audit_at` — who a resource belongs to does
not change — while **state** evidence may not (D12 and the index's
admissibility rule).

## D18 — A deleted account is linked through the deletion worker's run

**Decision.** About half of the primary accounts carry no identifier in evidence,
because they have been deleted (404, `profile: null`). Those are attributed from
`system_activity.csv`: candidates are `deletion_worker` `DELETE_RECORD` events
targeting `account_service` with `event_time` in
`[requested_at, reported_at + 30 min]`, excluding accounts linked to another
user. Each candidate is scored on four explainable features:

| Feature | Weight |
|---|---|
| `reported_result` matches the workflow's claim (COMPLETE↔SUCCESS, PARTIALLY_COMPLETE↔PARTIAL, NOT_STARTED↔FAILED) | +2 |
| the account also appears in the case's evidence file | +2 |
| the deletion is within 15 minutes of `reported_at` | +3 |
| timing-signature agreement, (agreeing − disagreeing) anchors | ×0.5 |

**Measured baseline.** Pure evidence linkage reaches 83 of the 111 gold sample
resources (74.8%). 18 of the 32 sample accounts carry no identifier at all, so
this layer is what covers them.

---

## D19 — The run's timing signature is learned, not hardcoded

**Decision.** Two things are learned from the data, with no labels: the seconds
at which a run's follow-up events sit relative to its account deletion, and the
longest plausible follow-up delay. Learning uses only cases whose account is
*already* linked by evidence, so the anchor time is known to be right.

**Learned bands.** From 348 anchor events across 238 qualifying cases, the
`(follow-up time − account deletion time) mod 60` histogram is:

```
 9s:18   10s:19   11s:4    20s:18   21s:90   22s:49
39s:7    40s:17   41s:2    50s:2    51s:34   52s:88
```

Twelve of sixty bins hold **all** the mass. Bins at or above the uniform
expectation (348/60 ≈ 5.8) are kept and widened by ±1s, because the bands are
evidently three seconds wide — a base offset plus about a second of jitter. The
accepted set is `{8..11, 19..23, 38..41, 50..53}`.

**Learned delay bound.** The same anchors give a maximum follow-up delay of
**3.38 hours** (largest observed delay plus 10% headroom); every learned delay
falls in the 20-minute-to-3.2-hour range.

**Why the bound matters more than the bands.** Sample `case_29` was initially
assigned the wrong account in a three-way tie at score 4.0. With the wrong
account, its four follow-up events sat at offsets of 101,361 to 104,750 seconds
— about **28 hours** — yet all four happened to land on a learned band
`mod 60` and so scored as agreements. Requiring the offset to be non-negative
and within the learned maximum turned that +2.0 into −2.0 and resolved the tie
to the correct account. Band membership alone is not a sufficient test.

## D20 — Each run also has its own cadence, which breaks ties between runs

**Decision.** The global bands say which offsets are plausible for *any* run.
A case's **own** cadence — the offsets its already-linked resources actually sit
at — says which ones *this* run used. When a case has a cadence, an event off
that cadence (beyond ±1s) is not part of that run, whatever the global bands say.

**Why — measured.** `analytics_5335` sits in `evidence_92`, which nine sample
cases share. Two candidates both looked plausible:

| case | account deleted | offset | mod 60 | in global band |
|---|---|---|---|---|
| case_21 | 11:01:53 | 1781 s | 41 | yes |
| case_23 | 11:10:55 | 1239 s | 39 | yes |

A tie, so the orphan was left unattributed. But `case_23`'s own run shows its
cadence outright: `export_7364` at offset 5272 (mod 52) and `search_898` at 6382
(mod 22). Its cadence is `{22, 52}`, and 39 is not on it. `case_21` has no other
linked resource, so it has no cadence and excludes nothing. `case_21` then wins
uniquely, which is the correct answer.

This also explains why bands must stay **pooled** rather than learned per event
type. Per-type learning gives `ANONYMIZE_RECORD` the bands `{20, 21, 51, 52}`,
yet every sample analytics orphan sits at 40–41. The runs come in at least two
shapes with different cadences; within `case_26`/`27`/`28`'s shape the analytics
event at 40–41 lines up with that run's own `DISABLE_DATA_FLOW` at 39–40. The
per-run cadence captures this; a per-type band would reject it.

## D21 — An unbreakable account tie falls back to a flagged best guess

**Decision.** Accounts are assigned jointly: an assignment is accepted only when
its score is strictly higher than that case's other remaining candidates *and*
strictly higher than any other unassigned case's score for the same account.
Accepting one removes it and the loop repeats. Remaining ties then take the best
remaining candidate at confidence 0.3, marked low-confidence and noted.

**Why.** A plausible resource id produces a verification step that can be graded;
an empty one cannot. The joint rule is what stops two cases claiming one account
— confirmed over the full 518 cases, where no account is claimed twice.

**Measured.** On the samples: 30 of 32 accounts assigned by the joint rule, all
correct, 2 left tied. The fallback then resolves both, one correctly
(`case_23` → `account_410`) and one not (`case_04` → `account_631`, where the
true `account_004` appears nowhere in the dataset). Net: **31 of 32 correct, 1
wrong, 0 unassigned.**

## D22 — Some gold resources are unreachable, and are not chased

**Decision.** Four sample gold resources appear in no evidence file and no
activity row. They are listed as unreachable and no heuristic is built to reach
them.

**Confirmed by grep** over the whole dataset — each appears only in
`sample_output.csv` itself:

| case | resource | found in |
|---|---|---|
| case_18 | `audit_record_6645` | nothing |
| case_20 | `audit_record_5569` | nothing |
| case_04 | `account_004` | nothing |
| case_07 | `support_001` | nothing |

`case_07`'s `support_001` is expected to come from
`delivery_correction_attachment.pdf` once document extraction lands, and
`case_04` is a hand-built case whose evidence is a screenshot. `analytics_901`
*is* in `evidence_56`, but it carries no identifier and `case_04` has no account
time to time it against, so it is unreachable for the same underlying reason.

Chasing these would mean inventing a rule that fits two or three specific rows —
exactly the case-family shortcut AGENTS.md §6.7 forbids.

## D23 — `created_at` is not an observation time

**Decision.** A record's observation time never comes from `created_at`,
`expires_at` or `last_write`. Those are properties of the record; the observation
happened when the snapshot was taken.

**Why — measured.** This was a real bug found by the attribution diagnostics.
`export_001` is linked to `user_08` by `owner_email` in
`customer_export_jobs_20260914.json` (captured 2026-09-14), but the record also
carries `created_at: 2026-08-04T16:11:00Z`. Treating that as the observation time
dated the link five weeks early, which put it outside sample `case_08`'s episode
window of `[2026-08-22, 2026-09-21]` — so a correctly parsed, correctly linked
gold resource was silently dropped. Fixing the field order recovered it and
raised sample recall from 94.6% to 95.5%.

`updated_at` is kept, because in a SQL snapshot it is the row's state time and
tracks the capture time closely.

## D24 — A finding requires positive evidence; unknown is not a violation

**Decision.** A finding is emitted only when evidence positively establishes the
thing policy objects to: the record is present, the flow is enabled, the backup
is restorable, the identifiers are exposed. A resource with no admissible
observation gets its verification step and nothing else.

**Why.** The alternative — treating unknown as a violation — manufactures
findings, and a spurious finding flips the whole case to `INCOMPLETE`, costing
the status, the remediation step and every verification citation at once. The
asymmetry is deliberate: absence is provable (explicit negative or coverage,
D12), presence is not inferable from silence.

**Measured.** On the samples this yields step precision of 98.9% against recall
of 95.9% — the pipeline under-reports rather than over-reports, which is the
right side to err on given how a false finding cascades.

---

## D25 — `RETAIN` means two different things, and the category decides which

**Decision.** `deletion_rules.csv` gives `SECURITY_AUDIT_LOG`,
`LEGAL_HOLD_RECORD` and `BACKUP_ARCHIVE` the same action, `RETAIN`, but they need
different steps. An audit log or legal hold yields `VERIFY_RECORD_PRESENT` only.
A backup archive yields the restore-blocking shape:
`REPORT_RESTORE_RISK` → `BLOCK_RESTORE` → `VERIFY_RESTORE_BLOCKED`.

**Why.** `rule_14`'s own condition says it: *"Restore access can be blocked"*.
The archive is retained; what gets closed is the path by which it could bring the
data back. Treating it like an audit log would emit `VERIFY_RECORD_PRESENT` and
never block the restore, which is precisely the failure the challenge is about.

A data flow has no row in the rules file at all, because it is a process rather
than a record: it is disabled, not deleted. That is modelled as a
pseudo-category rather than by inventing a rule.

The action column itself is always read from the CSV and never hardcoded.

## D26 — Three tiers of category resolution, evidence first

**Decision.** A resource's data category is resolved from (1) a category stated
in the evidence, (2) record-kind signals, (3) the resource prefix.

**Why tier 1 exists.** The evidence states the category outright, in exactly the
rules file's vocabulary: the handover record's category column, and the
`record_type` field of several JSON collections. Guessing from a prefix when the
data says the answer would be perverse.

**Why tier 2 is needed.** Two prefixes are genuinely ambiguous, and the
distinction changes the treatment:

| Prefix | Reading | Signal | Category | Action |
|---|---|---|---|---|
| `support` | attachment | `collection=ticket_attachments`, `storage_class=ticket_attachment`, `attachment_pii_scan`, `file_name`/`uploaded_by` | `SUPPORT_ATTACHMENT` | DELETE |
| `support` | legacy contact copy | `source=legacy_contact_index` with a `contact_query_*` event | `SECONDARY_IDENTIFIER` | DELETE |
| `support` | conversation | `support_conversations`, `tickets`, `message_pii_scan`, `message_excerpt` | `SUPPORT_MESSAGE` | REDACT |
| `analytics` | hashed contact lookup | `contact_lookup_*` event keyed on an email hash | `SECONDARY_IDENTIFIER` | DELETE |
| `analytics` | behavioural profile | anything else | `ANALYTICS_PROFILE` | ANONYMIZE |

**Measured.** Sample `case_12` expects `REPORT_REMAINING_RECORD` +
`DELETE_RECORD` on `analytics_9914`, not the anonymisation an analytics prefix
would suggest. The evidence for it is a log line reading
`event=contact_lookup_completed resource_id=analytics_9914 rows=1
correlation_key="44a65154..."` — a hashed identifier lookup, so a secondary copy
of the identifier rather than a profile.

## D27 — A resource outside every evidence file cites its catalog activity row

**Decision.** When no evidence file proves a resource's state, a step about it
cites the `activity_id` that attributed it.

**Why — found by the validator.** The full 518-case run initially produced two
`COMPLETE` verification steps with an empty `evidence_id`, which the contract
forbids. Both were resources attributed by the twelve `LINK_RESOURCE_IDENTITY`
catalog rows — `object_19` in `case_61` and `marketing_001` in `case_63` — and
neither appears in any evidence file. The catalog row *is* the only
participant-visible proof, and the contract explicitly permits citing a
`file_id`, an `activity_id` or an `audit_id`. This is what those twelve rows are
for (open item 13 from `data_facts.md` §7, now answered).

---

## D28 — An empty `COMPLETE` case is a warning, not a contract violation

**Decision.** The validator separates errors from warnings. A `COMPLETE` row with
an empty step array is a warning: valid, but nothing is proven.

**Why.** Exactly one case in 518 produces it — `case_542`, whose request reads
*"Could you send me a copy of the information held on my account? I still use it,
so please don't delete or change anything."* It is one of the ten non-deletion
requests, and with the intent classifier still stubbed to "every request
authorises deletion" it attributes nothing and so verifies nothing. The real
classifier will mark it `NOT_APPLICABLE` with `[]`. Conflating "nothing could be
attributed" with "deletion was not requested" would be the wrong fix: a genuine
deletion request that we fail to attribute must not be silently relabelled.

---

## D29 — The pipeline validates its own output on every run

**Decision.** `main.py` writes `output.csv` and immediately validates it,
exiting non-zero on any contract violation.

**Why.** It has already paid for itself twice in one session: it caught D27's
uncited verifications and D28's empty case on the first full run, both of which
the sample set never exercises because they occur in cases 61, 63 and 542.

---

## D30 — Target Python 3.11 syntax, and check it

**Decision.** The code must parse under Python 3.11, verified with
`ast.parse(..., feature_version=(3, 11))` across every file under `code/`.

**Why.** `requirements.txt` and `ruff.toml` target 3.11 while this machine runs
3.12. A backslash inside an f-string — `f"{'gold \\ pred':<16}"` in the
evaluation harness — is valid on 3.12 and a `SyntaxError` on 3.11. It ran here
and would have failed on a 3.11 grader, taking the whole submission with it.

## D31 — No sampling parameters are sent, and the cache supplies repeatability

**Decision.** Model calls set no `temperature`, `top_p` or `top_k`. Determinism
comes from the on-disk response cache plus a pinned `effort` per purpose.

**Why.** `temperature=0` is not available on either configured model. On
`claude-haiku-5-5` a non-default sampling value returns 400, and on
`claude-opus-5-5` the sampling parameters are removed entirely — sending one is
a request error, not a no-op. The spec for this layer asked for
`temperature=0`; it would have failed on the first call.

What replaces it: every call is keyed on
`sha256(model + prompt version + input)`, so a repeated question returns the
same stored answer without reaching the API at all. A warm run is therefore
*more* repeatable than `temperature=0` would have been, and free.

**Model choices and prices** (`config.yaml`, with the source and date beside
them): classification on `claude-haiku-5-5` at $0.10/$1M input and $0.50/$1M
output; document extraction on `claude-opus-5-5` at $4.00/$1M and $20.00/$1M.
The Haiku rates apply to prompts under 100K tokens, which every batch here is.

## D32 — Two classifier stages, and the rules stage must not decide a trap

**Decision.** Stage 1 decides a request by rule only when it has clear deletion
phrasing *and* carries no negation, no scoping word and none of the
other-request vocabulary. Everything else goes to the model.

**Measured.** On the full 518 cases, stage 1 decides **508** and the model sees
**10**, in a single batch of 10 distinct texts. Those 10 are exactly the ten
non-deletion requests — the same ten the `CLASSIFY_REQUEST` activity rows name,
arrived at independently.

**A substring trap found while building this.** The first cue list routed **46**
requests to the model instead of 10. The cause was the cue `"correct"` matching
*"Please apply the **correct** treatment to records covered by the request"* —
a sentence that appears in dozens of ordinary deletion requests and has nothing
to do with rectification. Replacing it with the actual rectification phrasings
(`correct my`, `correct it`, `correction`, `rectif`, `misspell`) cut the model's
work by 78% with no loss of coverage: all ten traps still route to the model.

**Why the negation guard is not optional.** Three of the ten state a deletion
keyword in order to refuse it ("I am not asking for deletion", "not a request to
erase it", "please don't delete or change anything"). A cue list decides those
backwards, which is why any text carrying both a deletion cue and a retention
statement is escalated rather than answered.

---

## D33 — The `CLASSIFY_REQUEST` rows are a cross-check, never an input

**Decision.** The ten `CLASSIFY_REQUEST` activity rows stating a request was
"classified as non-deletion" are compared with the classifier's output *after*
the fact, in `check_llm_layer.py`. They never reach the classifier.

**Why.** Reading them would be reading the organiser's own answer out of the
activity stream — a case-family shortcut of the kind AGENTS.md §6.7 forbids, and
one that would collapse the moment the hidden set contains a non-deletion
request the intake system never classified. As an independent check they are
valuable: two unrelated signals agreeing on the same ten cases is real
corroboration.

---

## D34 — A deletion request with nothing to verify is reported as a failure

**Decision.** This supersedes the softer form of D28. A case *classified as a
deletion request* that yields no attributed resources is an attribution failure
and is printed loudly in the run summary. A case the classifier never saw
(because no model was available) is not counted, since nothing was classified.

**Why.** D28 made an empty `COMPLETE` a warning because the only instance was
`case_542`, a non-deletion request the stubbed classifier could not recognise.
With the classifier in place that case is correctly `NOT_APPLICABLE` and the
warning disappears — the full 518-case run now validates with **zero** warnings.
Any future empty case is therefore a genuine gap, and should be noisy.

---

## D35 — A model may not invent a resource id

**Decision.** Every record returned by document extraction is validated before
it is believed. A `resource_id` is kept only if it matches the dataset's own id
shape *and* a known prefix. Anything else — a truncated id, a changed character,
a description instead of an id, an unknown prefix — is dropped and reported as a
warning, never repaired.

**Why.** A wrong character in a resource id attributes a record to a different
person, which is the exact failure the whole audit exists to catch. The
extraction prompt says so too: copy characters exactly, never complete or
correct an id, return `[]` when unsure. Code enforces it rather than trusting
it.

The parser is deliberately lenient about *shape* while strict about *identity*:
a status reported as `result` instead of `status`, or identifiers at the top
level instead of under `identifiers`, are both accepted. Losing a correctly-read
record to a schema quibble would be a waste; believing a wrongly-read id would
be a defect.

---

## D36 — `record_kind` is a category signal

**Decision.** The `record_kind` a document reports ("support attachment",
"backup archive") feeds the policy layer's tier-2 category resolution.

**Why — measured.** `delivery_correction_attachment.pdf` is the only evidence for
sample `case_07`'s `support_001`, and the gold answer deletes it, which requires
`SUPPORT_ATTACHMENT`. The signals that previously identified an attachment —
a `ticket_attachments` collection, a `ticket_attachment` storage class, an
`attachment_pii_scan` event — are all absent from a document record, so
`support_001` was classified `SUPPORT_MESSAGE` and redacted instead. Reading
`record_kind` fixes it, and the artefact supports it: the PDF is headed
"Attachment properties and upload history" and names the uploaded file.

---

## D40 — A non-deletion verdict needs high confidence; a deletion verdict does not

**Decision.** The pipeline accepts a non-deletion verdict only at confidence
`>= 0.9`. Below that the request is audited as a deletion anyway, and the
override is recorded on the decision and logged. A *deletion* verdict is never
overridden, at any confidence.

**Why the rule is one-sided.** The two errors do not cost the same. A wrong
`DELETION` costs a few steps on one case — the audit runs, finds little, and the
status may be wrong. A wrong `NOT_APPLICABLE` discards the **entire** case: its
status, every finding, every remediation and every verification, with no partial
credit and nothing downstream that can recover it.

**Measured.** With prompt v1 the live run marked sample `case_06` non-deletion at
confidence **0.60** and `case_25` at **0.85**, costing both cases outright and
dropping sample status accuracy from 31/32 to 29/32. Either would have been
caught by this rule alone.

**Outcome with v2.** Zero overrides fired: all ten non-deletion verdicts came
back at 0.95–0.97. The rule is a backstop that the improved prompt made
unnecessary on this run, which is exactly what a backstop should look like.

---

## D41 — Each prompt file gets its own cache namespace

**Decision.** Every cache key carries a fingerprint of *its own* prompt file:
`<name>@<version>+<sha256(body)[:12]>`. The document-extraction cache keeps the
extraction prompt's fingerprint in its path; the classifier cache keys on the
classifier prompt's.

**Why.** Before this, the classification cache was keyed on
`request_intent_classifier.md@<version>` while the document cache was keyed on
file content alone. That had two faults pulling in opposite directions: editing
the *extraction* prompt served stale extractions forever, and any wholesale
cache clear to fix that re-paid everything.

**Measured.** Bumping the classifier prompt from v1 to v2 cost **1 API call and
$0.0007** on the 32-case run — 15 cache hits for the untouched document
extractions. Without the separation the same edit would have re-paid all fifteen
vision calls, about **$0.58**. Including the body hash also means an edit that
forgets to bump the version still misses the cache instead of serving a stale
answer.

## D42 — Declared aliases are resolved, not dropped

**Decision.** A reference extracted from a document that is not a resource id
gets one chance: if the data catalog has *declared* it an alias, it is
translated to the resource id. Anything with no declared alias is still dropped.

**Why.** Documents show business references, not internal ids. An
object-storage browser lists `delivery_confirmation_19.pdf`; a deleted-account
screen shows `user_17`. Post-validation (D35) correctly refused both, because
neither is a resource id — but the catalog states what they are:

```
Attachment catalog confirmed object_19 (delivery_confirmation_19.pdf) ...
Data catalog linked tombstone_17 (user_17) to ... and user_17.
Data catalog linked export_1842 (NST-2026-0718-1842) to ... and user_18.
```

Parsing is generic — any `<resource_id> (<alias>)` pair in a catalog row — so no
alias value appears in the code. Self-aliases such as
`account_5762 (account_5762)` are skipped as carrying no information, which
leaves exactly **three** useful declarations in the dataset.

**Measured.** Two of the 24 dropped references were recovered, and both changed
a case:

| recovered | from | effect |
|---|---|---|
| `user_17` → `tombstone_17` | `deleted_account_reference_20260310.png` | `case_46`'s tombstone now cites `evidence_42`, the screen that shows it, instead of a case-level snapshot |
| `delivery_confirmation_19.pdf` → `object_19` | `object_storage_browser_20260213.png` | `case_61` COMPLETE → **INCOMPLETE**: the object was previously provable only by a catalog activity row (D27) and now has real state evidence |

The remaining 22 drops stay dropped and should: order numbers (`ORD-*`), support
case numbers (`CS-*`), a finance reference (`FIN-*`) and seven other object file
names, none of which the catalog declares.

`export_1842`'s alias `NST-2026-0718-1842` is declared but recovered nothing,
because the model never transcribed it — see the open items.

## D43 — A date printed inside a document is not the observation time

**Decision.** For document evidence the observation time is a **capture** time,
most specific first: a per-record "as of" value, then the artefact's own capture
time, then the manifest's `captured_at`. A date printed inside the record -
submitted, ordered, received, invoiced, dispatched - is kept as the
`record_dated_at` attribute and can never become the observation time. The
extraction prompt (v2) asks for the two separately, and the parser enforces it
regardless of what the model returns.

**Why — measured.** This is D23 again, one layer out. D23 removed `created_at`
from the observation-time fields because an export job created in August and seen
in a September snapshot was observed in September. The same error then arrived
from the model instead of the parser: reading
`delivery_correction_attachment.pdf`, it set

```
"observed_at": "2026-06-18T10:24:00Z"     // the PDF's "submitted 18 Jun 2026"
```

while the same PDF prints "captured 12 Sep 2026 07 30 UTC". Sample `case_07`'s
deletion episode runs 2026-08-24 to 2026-09-19, so an 18 June timestamp fell
outside it and the link to `support_001` was discarded as belonging to a
different episode — leaving the case wrongly `COMPLETE`.

**Result.** `case_07` is now an exact match to the gold answer, and sample status
accuracy reached 32/32.

## D44 — A record a document lists is present unless the document says otherwise

**Decision.** For document evidence, a record carrying its own resource id is
`present = True` by default. Only an explicit statement of absence — deleted,
removed, not found, expired, unavailable, no results, an empty state — makes it
absent. A `present: null` from the model becomes `True` in post-validation.

**Why.** This is the one place where the asymmetry of D24 flips, and it is worth
being explicit about why. D24 says a finding needs positive evidence and silence
stays unknown. For a *structured* source that is right: a log line that mentions
a resource without a result genuinely tells you nothing about whether it exists.
But an artefact is a **picture of a system**, and a row in a console or a line in
a register *is* the positive evidence — the record was there to be rendered. The
model leaving `status` blank says nothing about the record; it says the screen
had no status column.

A business status is explicitly not absence: "returned", "cancelled",
"refunded", "closed", "paid" and "dispatched" describe an order or a payment
while the record itself remains.

**Measured.** The model returned `present: null` for `support_001` with no status
shown. Under the old default that suppressed the finding even once D43 had fixed
the attribution, giving `case_07` two steps instead of gold's four. With this
default the case matches gold exactly, and across the 518 the change added three
more real findings (`case_33`, `case_34`, and five audit records in `case_45`)
without a single false one: sample step precision rose to 99.5%.

## D45 — Error analysis closed with no further fix

**Decision.** The error-analysis round ends without a code change. The three
remaining sample failures are not defects in any module, so there is nothing
general to fix.

**The three, with what the harness says about each:**

| case | cause | detail |
|---|---|---|
| `case_18` | `unrecoverable` | `audit_record_6645` appears in no observation and no activity row |
| `case_20` | `unrecoverable` | `audit_record_5569` likewise |
| `case_04` | `attribution` | `account_004` likewise; `analytics_901` is in `evidence_56` but carries no identifier, and `case_04` has no account time to date it against |

The `unrecoverable` label is derived from the data, not from a list: the harness
parses every artefact plus the activity stream and asks whether the gold resource
appears anywhere at all (D22). Two of the three are decided that way
automatically.

**Why `case_04` is not worth fixing.** Its gold account appears nowhere in the
participant data, so the only way to produce `account_004` would be to guess it
— and the low-confidence fallback already guesses, which is why the case shows
`account_631` as an extra. Any "fix" would have to privilege this case's shape,
which is the case-family shortcut AGENTS.md §6.7 forbids.

**Collateral the harness exposes.** `case_18` and `case_20` also show
`step_no` drift — `11 != 12`, `7 != 8` — on steps whose identity matches. That is
not an ordering defect: a missing unrecoverable finding shortens the array, so
every later step is numbered one lower. It is the reason `step_no` accuracy sits
at 97.9% while `state` and `evidence_id` are both 100%.
